# TraceHub v0.1.1 Requirements

[English](v0.1.1.md) | [简体中文](v0.1.1.zh-CN.md)

Status: Draft

## Goal

TraceHub stays aligned with active local Codex sessions without uploading or
retaining archived sessions. A user can browse sessions across devices,
explicitly destroy a session, and restore a shared session to Codex for
continuation or forking.

## Session semantics

TraceHub shares only active sessions present in a device's `sessions` directory
and does not maintain a server-side archived state.

| Local Codex operation | Observable TraceHub behavior |
|---|---|
| Create a session | Share the complete session |
| Continue a session | Share newly completed records |
| Archive a session | Delete the session from TraceHub |
| Unarchive a session | Share the session again as active |
| Permanently delete a session | Delete the session from TraceHub |
| Fork a session | Share a new session while preserving the fork relationship |
| Restore a session | Write the original session into the target device's `sessions` directory |

## Requirements

### REQ-008: Share only active Codex sessions

Status: Draft

A user can have TraceHub share only active Codex sessions without uploading or
retaining locally archived sessions.

Acceptance criteria:

- The default synchronization source is only `sessions` under the configured
  Codex root.
- Files in `archived_sessions` are not read, uploaded, or shown as shared
  sessions.
- Newly created and continued active sessions can be shared completely and
  incrementally, respectively.
- Repeated synchronization of the same unchanged active session creates no
  duplicate session or event.

### REQ-009: Align local removal and restoration

Status: Draft

After a successful synchronization, sessions contributed by a device match that
device's current active session set. Local archiving and permanent deletion both
delete the TraceHub copy; unarchiving allows it to be shared again.

Acceptance criteria:

- After a session disappears from `sessions`, the next successful
  synchronization deletes that device's corresponding TraceHub session.
- Deletion makes session content, search indexes, tool output, and exports
  inaccessible.
- After an archived session returns to `sessions`, the next synchronization can
  share it again from the beginning.
- Synchronizing one device cannot delete sessions contributed by another device.
- Repeating synchronization of the same active session set is idempotent.

### REQ-010: Fail deletion alignment safely

Status: Draft

TraceHub may align deletions from a local session set only when the client can
establish that discovery and synchronization completed successfully.

Acceptance criteria:

- A missing or unreadable Codex root or `sessions` directory, or an interrupted
  scan, does not delete server sessions.
- Invalid session identity, duplicate files, parsing failure, or upload failure
  prevents deletion alignment for that synchronization.
- Deletion alignment does not occur if the server does not completely accept
  the active session set.
- Failure is explicit and an empty or incomplete set is never interpreted as
  the user deleting all sessions.
- A session whose upload failed is not treated as deleted in the same run.

### REQ-011: Browse and understand shared sessions

Status: Draft

An authorized user can browse, search, filter, inspect, and page through shared
sessions across devices while understanding their source and fork relationships.

Acceptance criteria:

- The user can list sessions, perform text search, and inspect session details.
- Sessions can be filtered by source device, time range, working context, and
  whether they are forks.
- Lists and details identify the session UUID, source device, time range,
  working context, and last synchronization time.
- When fork information exists, details identify the parent session and
  queryable derived relationships.
- Long sessions can be read with a stable cursor while preserving order without
  duplicate events or omitted content.
- User messages, assistant messages, and tool activity remain distinguishable;
  reasoning is never returned through browsing interfaces.
- Complete tool output is returned only after an explicit request and remains
  subject to the per-response size limit.
- All historical content remains explicitly marked as untrusted data.

### REQ-012: Explicitly destroy a shared session

Status: Draft

An authorized user can permanently delete a shared session, but the system must
require explicit confirmation before doing so.

Acceptance criteria:

- Deletion identifies the source device and session UUID and requires
  confirmation that cannot be omitted.
- After deletion, the session is unavailable through listing, search, details,
  paged reading, tool output, and export.
- A failed deletion does not leave content, indexes, and archive data in a
  partially deleted state.
- An unchanged local file on the source device does not silently restore an
  explicitly destroyed session during ordinary synchronization.
- The user can explicitly re-share a session that still exists locally or was
  restored, allowing it to upload again from the beginning.
- The confirmation does not include complete session content.

### REQ-013: Restore a shared session to Codex

Status: Draft

A user can download a shared session on a target device and restore it to Codex
so that Codex can continue it or create a fork.

Acceptance criteria:

- The restored result byte-for-byte matches the complete original JSONL records
  preserved by TraceHub.
- The restored file is written to the standard `sessions` location under the
  target Codex root, not to `archived_sessions`.
- Download, decryption, validation, or write failure leaves no partial session
  visible to Codex.
- An existing session with the same UUID at the target location causes an
  explicit error and is not overwritten.
- Codex can discover the restored session and allow the user to continue or
  fork it.
- New content and forks created after restoration can be shared by a later
  synchronization.
- TraceHub preserves the original source device, restoration target device, and
  known fork relationships without automatically merging session content across
  devices.

## Out of scope

- Uploading or browsing `archived_sessions`.
- Server-side archived state, trash, or delayed deletion.
- A Web UI.
- Continuous background synchronization or automatic remote-device mutation.
- Automatic merging of session content from different devices.
- Agents other than Codex.
- Team permissions, multi-user tenancy, high availability, or distributed
  operation.

## Version acceptance

- Complete an end-to-end create, append, archive, unarchive, and permanent-delete
  flow with synthetic Codex JSONL.
- Verify that discovery, parsing, and upload failures cannot cause server-side
  session deletion.
- After device A uploads, device B can search, filter, inspect details, and read
  multiple pages.
- The restored result byte-for-byte matches the source JSONL and Codex can
  discover it.
- After deletion, ciphertext, derived events, search results, tool output, and
  export are all inaccessible.
- `make check`, `actionlint`, and `git diff --check` all pass.
