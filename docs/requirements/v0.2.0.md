# TraceHub v0.2.0 Requirements

[English](v0.2.0.md) | [简体中文](v0.2.0.zh-CN.md)

Status: Draft

## Goal

TraceHub stays aligned with active local Codex sessions without synchronizing
archived sessions. A user can understand session and fork relationships across
devices, explicitly keep a destroyed session absent, and restore a shared
session to Codex for continuation or forking.

## Session semantics

After a successful synchronization, the sessions contributed by a device equal
that device's current active `sessions` set, excluding sessions explicitly
destroyed under REQ-014. TraceHub does not maintain a server-side archived
session state.

| Operation | Observable TraceHub behavior |
|---|---|
| Create a local session | Share its complete records |
| Continue a local session | Share its newly completed records |
| Archive or permanently delete a local session | Delete that device's shared copy |
| Unarchive a local session | Share it again unless it is explicitly destroyed |
| Explicitly destroy a shared session | Delete it and suppress ordinary re-sharing |
| Explicitly re-share a session | Clear suppression and share it from the beginning |
| Fork a local session | Share a new session and preserve its known parent relationship |
| Restore a shared session | Write its synchronized records into the target device's `sessions` directory |

## Requirements

### REQ-008: Share only active Codex sessions

Status: Draft

A user can have TraceHub synchronize active Codex sessions without synchronizing
locally archived sessions.

Acceptance criteria:

- Synchronization discovers sessions only under `sessions` in the configured
  Codex root.
- Synchronization does not read or upload files under `archived_sessions`, and
  those files are not shown as shared sessions.
- Newly created and continued active sessions can be shared completely and
  incrementally, respectively.
- Repeated synchronization of the same unchanged active session creates no
  duplicate session or event.

### REQ-009: Align local session removal and return

Status: Draft

After a successful synchronization, TraceHub aligns the sessions contributed by
one device with that device's current active session set, except for explicit
destruction recorded under REQ-014.

Acceptance criteria:

- After a session disappears from `sessions`, the next successful
  synchronization deletes that device's corresponding shared session.
- Deletion removes the session's encrypted source chunks, derived events, and
  search index entries and makes details, tool output, and export unavailable.
- If the same session later returns to `sessions`, the next successful
  synchronization shares it again from the beginning unless REQ-014 suppresses
  it.
- Synchronizing one device cannot delete or suppress a session contributed by
  another device.
- Repeating synchronization of the same active session set is idempotent.

### REQ-010: Fail session-set alignment safely

Status: Draft

TraceHub aligns deletions from a local active session set only after the client
and server establish that discovery and synchronization completed successfully.

Acceptance criteria:

- A missing or unreadable Codex root or `sessions` directory, or an interrupted
  scan, does not delete server sessions.
- Invalid session identity, duplicate files, parsing failure, or upload failure
  prevents deletion alignment for that synchronization.
- Deletion alignment does not occur unless the server accepts the complete
  active session set for the device.
- Failure is reported explicitly; an incomplete set is never interpreted as the
  user deleting the omitted sessions.
- A valid empty set authorizes deletion only after an existing, readable
  `sessions` directory is completely scanned and the server accepts that empty
  set as complete.
- A session whose upload failed is not treated as deleted in the same run.

### REQ-011: Browse and understand shared sessions

Status: Draft

An authorized user can browse, search, filter, inspect, and page through shared
sessions across devices while understanding their source and fork relationships.

Acceptance criteria:

- Sessions can be filtered by exact source device, an event-time interval that
  overlaps the session's known time range, source-reported repository or working
  directory, and whether the session has a known parent.
- Lists and details identify the session UUID, source device, known time range,
  source-reported working context, and last successful synchronization time.
- When fork metadata exists, details identify the parent and direct child
  sessions by source device and session UUID.
- For an unchanged result set, a list cursor preserves deterministic order and
  returns every matching session once across pages.
- For a session unchanged between page requests, an event cursor preserves event
  order without duplicate or omitted content.
- User messages, assistant messages, and tool activity remain distinguishable;
  reasoning is never returned through browsing interfaces.
- Complete tool output is returned only after an explicit request and is limited
  to 256 KiB per response.
- All historical content remains explicitly marked as untrusted data.

### REQ-013: Restore a shared session to Codex

Status: Draft

An authorized user can restore a shared session on a target device so that Codex
can continue it or create a fork.

Acceptance criteria:

- The restored bytes equal the concatenation of complete original JSONL records
  accepted by the last successful synchronization of the selected device and
  session UUID.
- The restored file is written to the standard dated location under `sessions`
  in the target Codex root, not to `archived_sessions`.
- Before writing, TraceHub rejects the restore if the same session UUID already
  exists anywhere under `sessions` or `archived_sessions` in the target Codex
  root; no existing file is overwritten.
- Download, decryption, validation, or write failure leaves no partial session
  visible to Codex.
- The Codex installation used for release verification can discover the restored
  session and allow the user to continue or fork it.
- New complete records and forks created after restoration can be shared by a
  later synchronization.
- When the restored file is later shared, TraceHub identifies the original
  contributor and the target device as separate contributions with the same
  session UUID; it preserves known fork relationships and does not merge their
  content.

### REQ-014: Keep an explicitly destroyed session absent

Status: Draft

An authorized user can explicitly destroy one device's shared session and keep
ordinary synchronization from silently sharing the local copy again until the
user explicitly re-shares it.

Acceptance criteria:

- Explicit destruction identifies the source device and session UUID and stores
  only the identity needed to suppress ordinary re-sharing, not session content.
- After explicit destruction, ordinary synchronization leaves the session
  absent even when an unchanged local file remains in `sessions` or later
  returns there.
- Suppression for one source device does not affect a contribution with the same
  session UUID from another device.
- An explicit re-share requires the source device and session UUID, fails if no
  matching active local file exists, and otherwise clears suppression so the
  next successful synchronization shares the session from the beginning.
- Failed destruction leaves the session and its prior suppression state
  unchanged; failed re-share leaves suppression in place.
- Suppression has no automatic expiry and remains until explicit re-share.

## Out of scope

- Uploading or browsing `archived_sessions`.
- A server-side archived session state, trash, or delayed deletion.
- A Web UI.
- Continuous background synchronization or automatic remote-device mutation.
- Automatic merging of session content from different devices.
- Agents other than Codex.
- Team permissions, multi-user tenancy, high availability, or distributed
  operation.

## Version acceptance

- Complete an end-to-end create, append, archive, unarchive, and local-delete
  flow with synthetic Codex JSONL.
- Verify that discovery, parsing, upload, and server-acceptance failures cannot
  cause server-side session deletion; separately verify a completely scanned,
  valid empty set.
- Explicitly destroy a session, verify ordinary synchronization keeps it absent,
  explicitly re-share it, and verify the next successful synchronization shares
  it from the beginning.
- After device A uploads a parent and fork, device B can filter, inspect their
  relationship, and read multiple pages without duplicate or omitted results
  while the data remains unchanged.
- Restore the records accepted by the last successful synchronization, verify
  their exact bytes and Codex discovery, and verify UUID collision rejection.
- After deletion, encrypted source chunks, derived events, search results, tool
  output, and export are all unavailable.
- `make check`, `actionlint`, and `git diff --check` all pass.
